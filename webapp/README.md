三个页签，按任务组织：

### 环境（LARK_ENV）

* `prod`（默认）— 读写真实的 3.1 / 5.6 / 5.x。
* `dev` — 3.1 / 5.6 / 已复制的 5.x 解析到**测试副本**（`config.js devTables`）。
  页面右上角有醒目的 **DEV 测试环境** 徽标；提交请求携带环境标识，
  与服务端不一致会被拒绝（防止旧页签误写另一环境）。
* **dev 绝不写生产 5.x**：只有拥有 dev 副本的出库计划表才允许建/挂行程
  （现有 `5.2 BESTAR-CAL` 副本 `tblJaXrkXhZr3R6N` → BESTAR / CAL-5505 全链路
  可测）；其余仓库在 dev 下预约/行程操作停用（板数核对仍可用），界面有提示。
  要为其他仓库启用：在 Lark 复制对应 5.x 表，然后在 `config.js` 的
  `devTables` + 三个 dev 字段映射里补上同名键（详见 config 注释）。

## ⚡ 预约同步（核心工作流）

实现 `docs/40 Workflows/Appointment Sync Runbook.md`，核心代码
`webapp/appointment_sync.py`（决策树在 `_plan_row()`，提交分五阶段在
`commit()`，均有逐行注释）。

**输入格式**（一行一票，Tab/空格均可，直接从 Excel 粘贴）：

```
柜号/AWB  目的地路线  实际板数  箱数  [ISA  MM/DD/YYYY HH:MM  [时区]]
OOCU9020713B  YEG2  4  141
CXDU2185835   YEG2  2  135  147204024984  07/27/2026 08:00 MDT
```

* 末两个数字必须是 **[实际板数] [箱数]** —— 缺一个（如 `CSGU6249922 YVR4  96`）
  整批拒绝执行，直到修正（逐行红字提示）。
* ISA 和预约时间必须**成对**出现；时区（PDT/MDT…）接受但**不入库**（5.6
  `复制时间列` 存纯文本 `YYYY/MM/DD HH:MM`，与现存行一致）。

**每行的处理逻辑**（详见 Runbook / Decision Tree）：

1. 按 柜号+路线+仓库 在 3.1 找**唯一**行（0 行或多行 → 报错不处理）。
2. `实际板数` 为空 → 填入提供值；与 `预计板数` 差 >2 → **W1** 警告。
   不为空 → **绝不覆盖**；差 >2 → **W2** 警告（注明未覆盖）。
3. 已挂出库计划 → 核对 ISA+时间：一致→不动；不一致→**更新所关联的 5.6
   记录**（影响同行程所有货件，界面有提示）。
4. 未挂计划且给了 ISA → 5.6 找该 ISA：有行程→挂靠（行程总板数 >28 →
   **W3**）；有 ISA 无行程→新建行程并互联；ISA 不存在→创建预约（目的地
   必须是 5.6 现有选项，绝不自动新增）+ 新建行程 + 互联。
5. 同一 ISA 的多行 = **一组**（一个预约多柜）：只建一条 5.6 / 一条行程，
   全组挂同一行程；组内时间不一致 → 拦截。

**守卫**：预检只读；执行只写勾选行；执行前服务端**重新预检**，与勾选时
情况不一致的行自动跳过（`情况已变化`）；写后**回读核实**并逐行标注；
全部警告最后集中汇总（可复制）。

**进度与防卡死**（2026-07-31 重构，解决「执行按钮卡住」）：

* 预检/执行都是**服务端后台任务**：提交立即返回任务号，页面每 0.5s 轮询
  一次进度 —— 阶段名（复检 → 写入 1/5…5/5 → 回读核实）、第 N/M 行、
  当前柜号、已用秒数、进度条全程可见。
* **同一时刻只允许一个写入任务**（single-flight）：重复点击/另开页签提交
  会被明确拒绝并自动跟踪现有任务进度，而不是无声排队（旧版卡死主因之一）。
* **刷新页面不丢任务**：写入进行中刷新/误关后重开，页面自动重连该任务，
  完成后照常渲染结果；写入中关闭页面会弹出确认。
* 网络抖动免疫：单次 Feishu 调用 30s 超时；读请求与带 `client_token` 的写
  请求自动重试（同 token 重发，Feishu 幂等去重）；套接字中断不再让请求
  线程无限挂起。轮询失败只提示「重试中」，服务端任务不受影响。

**API**：`GET /api/sync/meta` · `POST /api/sync/plan` / `POST /api/sync/commit`
（都立即返回 `{job}`）· `GET /api/sync/job?id=<id|latest>`（轮询进度，
完成时附带结果）。commit 需环境匹配。

| 仓库 → 预约账号 / 出库计划表 映射 | `webapp/appointment_sync.py` 顶部 `WAREHOUSES`（与 `config.js warehouses` 保持一致） | **是** |

| 字段改名（飞书里改了列名） | `config.js` 对应字段名 + `appointment_sync.py` 的 `F31/F56` | **是** |
| 输入行格式、解析规则 | `webapp/appointment_*.py` 的 `parse_line`（前端即时校验镜像在 `static/app.js`，两处同步改） | **是** |
| 复制时间列 **存储格式** | `appointment_sync.py` 的 `store_time()`（现为 `MM/DD/YYYY HH:MM`，2026-08-04 指定；比对用 `norm_time()`，新旧格式都能读） | **是** |
| 界面文案 / 列 / 样式 | `webapp/static/`（app.js / index.html / style.css） | 否（刷新页面） |
| 配色（浅色/深色） | `style.css` 顶部两个 token 块（`:root` / `:root[data-theme="dark"]`）—— 组件规则一律用 `var(--x)`，不写死颜色 | 否（刷新页面） |

**主题**：右上角按钮循环 自动 / 浅色 / 深色（记在 `localStorage.larkTheme`；
`自动` 跟随系统）。`<head>` 里有一段极小的内联脚本在首次绘制前就贴上
`data-theme`，所以深色用户不会看到白屏闪一下。

> ⚠ 改样式时的两个坑（都踩过）：
> 1. **纯色背景一律用 `background-color:`，不要用 `background:` 简写**，并且
>    **不要给颜色属性加 `transition`** —— 简写/过渡 + `var()` 会让浏览器在
>    切换主题时**不重新求值**，颜色卡在旧主题上（2026-08-04 实测）。渐变
>    （`--topbar`）用 `background-image:`。
> 2. 表格宽度：`.wrap`/`.tabs` 已改为**跟随浏览器宽度**（无固定上限，保留边距），
>    `.synctable` 允许换行（含 `.sub`），这样一整行不用横向滚动就能看完。

> 经验法则：**选项类的东西在飞书里改**（网页读的是实时选项，绝不硬编码）；
> **结构类的东西改 Python + config.js 后重启**；**纯前端改完刷新即可**。
> `config.js enums` 只服务 Node 运行手册，网页不读它。

## 工作流与职责划分（2026-08-04 重组，消除页签重叠）

按操作顺序排列的页签，**每张表只有一个写入入口**：

| 页签 | 写什么 | 绝不做什么 |
|---|---|---|
| **① 新建预约** | 创建 5.6 预约记录（缺失的 ISA） | 不改 3.1 · 不建出库计划 · 不改已存在预约 |
| **② 计划同步** | 3.1 实际板数（只填空）· 新建/挂靠 5.x 出库计划 · 更新**已关联**预约的 ISA/时间 | **绝不创建 5.6 记录** — ISA 不存在时拦截并指回 ① |

**拆行（同柜号+同路线多条 3.1）**：② 允许同柜号+路线出现多行 — 按
**箱数**（提供值 vs 表内 箱数，空=0）精确区分；箱数并列时再按**板数**
（提供值 vs 表内 实际板数）。两个键都是「你提供的数 vs 飞书上的数」，
绝不用预计板数；仍分不开 → 该行拦截并列出候选，绝不猜。两行若匹配到
同一条记录 → 双双拦截。测试：`npm run test:split`（真实拆行数据集）。
| **③ 核对** | 无（完全只读） | 沿 3.1 → 出库计划 → 预约 逐层核对，标记 无计划/缺预约/ISA不符/时间不符/目的地不符/账号不符/共用 |
| 🔍 库存查询 / 📄 文件解析 | 无（只读；解析结果一键送 ①/②） | 旧的「上传到 5.6」按钮及 `/api/upload` 等端点已移除 |

ISA 唯一性在 ② 也有护栏：4A 改写预约 ISA 时，若目标 ISA 已存在于另一条
5.6 记录 → 拦截（否则会造出重复 ISA）。措辞注意：②里的「新建出库计划」
是 5.x 派送计划记录，**不是**新建预约 — 早期版本写作「新建行程」曾引起误解。

## ➕ 新建预约（仅 5.6）

独立的轻量步骤（`webapp/appointment_create.py`）：粘贴
`目的地 → ISA → MM/DD/YYYY HH:MM [时区]` 行 + 选仓库（→ 预约账号，VAST→元浩），
只创建 5.6 里**不存在**的 ISA — 不碰 3.1、不建行程。

**ISA 唯一性（三层去重，实测数据支撑）**：

1. **同批**：同一 ISA 多行只建一次；目的地/时间不一致则整组拦截。
2. **查表**：预检逐个 ISA 搜索 5.6（并行）。已存在但内容不同 → 跳过 + 警告
   （本界面不做修改，去「预约同步」处理）。
3. **跨波次**：⚠ Bitable 搜索索引对新建记录有 **约 5–7.5 秒延迟**
  （2026-08-04 dev 实测 avg 5.5s / max 7.5s）——只靠搜索去重，紧接着提交的
   第二波**会**重复创建。因此每次创建同时登记进程内 recent-creates 缓存
  （TTL 10 分钟），预检/执行先查缓存再查表；执行还在全局写锁下复检，
   并发提交也只会建一条（集成测试含双线程竞速用例）。
   *边界*：缓存在服务器进程内 — 若在盲窗几秒内重启服务器再提交第二波，
   仍可能漏判；正常使用（单服务器常驻）不会遇到。

写后回读核实并**测量每条的索引可见延迟**，结果里直接展示。
API：`POST /api/create56/plan` / `POST /api/create56/commit`（job 模式，
与预约同步共用进度轮询和写入单飞）。测试：`npm run test:create56`
（用真实两波数据，验证重复 ISA 只建一次）。

## 它怎么工作

```
浏览器 ──HTTP──> server.py ──HTTPS──> open.feishu.cn (Bitable OpenAPI)
                     │
                     ├── config/config.js   ← baseToken + 表注册表（单一事实来源）
                     └── config/secrets.txt ← App ID / Secret（仅服务端读取）
```

* `lark_client.py` —— 飞书 API 客户端：鉴权+token 缓存、视图/字段元数据、搜索、
  值格式化、环境解析（`table_id()`）。本模块**没有写方法**；写入模块直接走
  `_api` 并持有全局 `WRITE_LOCK`。
* `appointment_sync.py` —— ⚡ 预约同步核心（解析 / 只读预检 / 分阶段提交）。
* `upload_56.py` —— 文件上传 → 5.6 登记（dry-run + 守卫）。
* `server.py` —— 极简 HTTP 服务 + JSON API，只监听 `127.0.0.1`。
* `static/` —— 前端（原生 JS，无框架、无外部资源）。

### 安全

* **密钥只在服务端。** App ID/Secret 从 `config/secrets.txt` 读取用于换取
  `tenant_access_token`，**绝不下发到浏览器**，也不写日志。
* **只绑定 127.0.0.1**，不对局域网暴露（因为它能读生产凭据）。
* 查询/预检全部只读；写入只有两条路径（预约同步执行、上传 5.6 确认），
  都要求显式点击 + 确认，且全程序列化（进程级写锁）+ 幂等 client_token。

## ⚠️ 关于「视图」的重要说明

飞书 API **无法在一个视图内做搜索**：只要你传了自己的 `filter`，它就会
**覆盖掉视图自带的过滤条件**（在本 Base 上对 `/records/search` 和 `/records`
两个接口都实测确认过）。

所以本工具的做法是：

1. 先在**全表**按柜号/ISA 搜索（命中通常只有几十行）；
2. 再把所选**视图自身的过滤条件**在本地逐行判定，筛掉不属于该视图的行；
3. 同时按视图的 `hidden_fields` 隐藏该视图不显示的列。

结果里会显示 `全表 N → 视图内 M（排除 X）`，做到可验证。

**如果某个条件本地无法判定**（未知字段、未支持的操作符），界面会明确提示
`⚠ 无法本地判定的条件：xxx（结果可能偏宽）`，**绝不静默给出错误结果**。

已支持的视图条件操作符：`contains` / `doesNotContain` / `is` / `isNot` /
`isEmpty` / `isNotEmpty`，其中单选/多选/公式选项字段会自动做
option-id → 选项名 映射。

## 📄 上传文件自动识别

把 Excel/CSV 拖进页面上的上传区（或点「选择文件」），自动提取六个字段：

| 字段 | 表头别名（部分） | 识别方式 |
|---|---|---|
| 柜号 / AWB | 柜号、货柜号、**装货明细**、AWB | 表头列 → 行内标注 → 正则（`ABCD1234567`／带后缀 `…B`／`093-9992123`）|
| 客户批次号 | 客户批次号、批次号、批次 | 表头列 → 行内标注（`客户批次号：JF-US26038B`）→ 正则 |
| 仓库供应商 | 仓库供应商、操作仓库、供应商 | 表头列 → 与 3.1 的**实时选项**比对 |
| 目的地路线 | 目的地路线、派送目的地、仓库代码、**仓库** | 表头列 → 与 3.1 的**实时选项**比对，`CA-YVR4`→`YVR4` |
| 预约时间 | 预约时间、预约、时间 | 表头列（含 Excel 序列号换算）→ 日期正则 |
| ISA | ISA、**预约号**、预约编号、预约单号 | 表头列 → `ISA:123456789` / `ISA-000123` / 纯数字列 |

> **`预约号` 就是 ISA**，`预约/时间` 都算预约时间，`仓库`（值形如 YYC4/YEG2）算目的地路线 —— 均按现场口径配置。
> 别名**最长优先**，所以 `仓库供应商` 仍归「仓库供应商」、`仓库代码` 仍归「目的地路线」，不会互相抢。

**支持的日期格式**：`2026-07-24 09:00`、`2026/07/24`、**`07/24/2026 09:00 MDT`**（月在前，
自动保留 MDT/PDT/EST 等时区标记）、Excel 日期序列号。

### 仓库供应商下拉框

| 解析结果 | 下拉框 | 控制台 |
|---|---|---|

### 📦 柜号明细表（每柜对应自己的预约）

除了上面的汇总卡片，还会输出一张**逐柜明细表**，把不同格式的 Excel 统一成一张表：

| 柜号 | 目的地路线 | 预约号/ISA | 预约时间 | 板数 |
|---|---|---|---|---|

- **一柜一约**：每行一个柜号，带自己的预约号与时间。
- **多柜分组**：一个 `装货明细` 单元格里有多个柜号（换行或 `A-10P/B-2P` 形式），
  共用该行的预约号与预约时间，打「分组」标记。
- **板数**（`13P` / `13P-9` / `4箱` / `1箱散货`）原样保留，按柜归属（不串到下一个柜号）。
- 快递/私人地址行（UPS、PUROLATOR、AST…、私人地址码）没有预约的，预约号/时间显示 `Null`。
- 每行右侧「查询」按钮，一键拿该柜号去 3.1 查。
- 每行右侧「**上传**」按钮 + 上方「**预演上传到 5.6（dry-run）**」按钮 →
  写入飞书 **`5.6 预约表`**。见下节。

### ⬆ 上传到 5.6 预约表（含 dry-run + 守卫）

把解析出的每条「柜号→路线→预约号→时间」登记成 5.6 的预约记录。全部写入都有守卫，
逻辑在 `webapp/upload_56.py`：

- **先 dry-run**：点「预演上传到 5.6」→ 出一张清单，每行标注动作：
  `待新建` / `跳过（已存在）` / `拦截`，并给出汇总（新建 X · 跳过 Y · 拦截 Z）。**不写任何东西**。
- **按 ISA 去重**：预约号已存在于 5.6 → 跳过（`console.log("当前派送记录已存在")`）；
  同一批次里同一预约号也只建一次（分组的多柜共用一个预约）。
- **校验目的地**：路线必须是 5.6「目的地」的现有选项；UPS/PUROLATOR/AST/私人地址等 → 拦截，
  **绝不自动新建选项**。
- **预约账号**：取上方所选「仓库供应商」，做映射校验（**VAST→元浩**；`CAL-5505`/`TOR-1140`
  非合法账号 → 拦截）。
- **字段格式**：`ISA` 写为数字；`目的地`/`预约账号` 写为合法单选；`复制时间列` 写为
  文本 `YYYY/MM/DD HH:MM`（对齐 5.6 现存格式）。
- **提交**：dry-run 后若有「待新建」，出现「确认写入 5.6（新建 N 条）」按钮 →
  二次确认 → `batch_create`（带 `client_token` 幂等）。或用每行「上传」按钮逐条写。

API：`POST /api/dryrun_56`（只读预演）、`POST /api/commit_56`（批量写）、
`POST /api/upload`（单条，走同一守卫）。

#### 兼容的两种表格布局（自动识别）

| 布局 | 样子 | 柜号从哪来 |
|---|---|---|
| **A · 出库计划** | 一行一票，`仓库\|预约号\|预约时间\|装货明细`，柜号在 `装货明细` 单元格里（可多柜） | 单元格内正则 |
| **B · 派送计划** | `柜号 CNTR：<柜号>` 标题行 + 其下若干 `派送仓点\|总托数\|预约号\|预约时间` 行；多个柜号纵向堆叠 | 标题行，向下管辖到下一个标题行 |

两种布局都归一成上面同一张明细表。新增识别的表头别名：`派送仓点`（目的地路线）、
`总托数/板数`（板数）、`预约号`（ISA）。`预约号` 列若是文字（如「有了预约时间更新」）
则判为无效 → `Null`。

**识别不到的字段返回 `Null`**（界面上红色 `Null`）。识别到多个值时会显示
「共 N 个不同值」可展开，主值取出现次数最多的那个。每个值都标注了来源
（哪张表的哪一列 / 行内标注 / 正则扫描），便于核对。

识别完可以一键「用柜号查询」或「用 ISA 查询」，直接把值送进上面的查询框。

支持格式：`.xlsx` / `.xlsm` / `.csv` / `.tsv` / `.txt`（`.xls` 请先另存为 `.xlsx`）。

### 识别策略（为什么这样设计）

1. **优先表头**：找到表头行后按列取值。别名匹配**最长优先**，所以 `仓库代码`
   会被识别成「目的地路线」而不是「仓库供应商」。
2. **表头需至少命中 2 个别名**（沿用项目里 `parse-plan.js` 的成熟规则）。
   否则像 `客户批次号：JF-US26038B` 这种标题单元格会被误当成表头，导致整列取错值。
3. **行内标注**：`标签：值` 形式的标题块单独抽取。
4. **正则兜底**：以上都没有时，全表扫描正则 + 实时选项比对。

xlsx 读取优先用 `openpyxl`（能正确处理日期单元格），没装则自动回退到
`zipfile + XML` 的标准库解析器 —— 所以**依然是零硬依赖**。

> **柜号正则的一个坑**：不能用 `\b` 收尾。Python 的 `\w` 把中文算作单词字符，
> `UETU8792061转运` 里 `1` 和 `转` 之间没有词边界，用 `\b` 会**整个匹配不到**。
> 因此用的是 `(?<![A-Z0-9])([A-Z]{4}\d{7}[A-Z]?)(?![A-Z])`，同时让
> `MATU45919300` 仍能取出 `MATU4591930`。
> 另外一个单元格里可能有**多个**柜号，必须 `finditer` 而不是 `search`。

## 使用要点

* **柜号建议用「包含」匹配。** 表里柜号常带后缀（例如 `CAJU5283296` 实际存为
  `CAJU5283296A` / `CAJU5283296B`），精确匹配会查不到。命中后界面会显示
  「匹配值」，把实际柜号列出来。
* 一个柜号通常对应**多行**（按目的地路线拆分）。
* 点击结果表任意一行可展开该记录的**全部非空字段**。
* 时间字段按 `America/Edmonton`（山区时间）渲染，可用环境变量 `LARK_TZ` 改。

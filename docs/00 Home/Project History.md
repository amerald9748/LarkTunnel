## 2026-07-22 · 基础与第一次生产写入

**情境**：用户要把一套 Lark 批量操作工具从别的项目迁出，目标工作流是"到仓预约
同步"。明确要求：*"这是生产环境，任何改动/测试前先告诉我。"*

- **Safe mode 默认开**（Node 包装层 `src/lark/client.js` 的 `gatedWrite`）：
  写入默认只打印意图不发送 → 后来 webapp 继承为"预检只读 + 显式提交"的范式。
- **单一事实来源 `config/config.js`**：表 id、字段名、仓库映射集中一处，Python
  侧用正则读取同一文件，避免两套常量漂移。
- **CAL-5505 → BESTAR**（用户确认）；**TOR-1140 无预约账号/计划表** → 刻意
  "只做板数核对"，工具拒绝为它猜测路由。
- 现场核实字段：`5.4 VAST-VAN-01` / `5.5 GFL-VAN-02` 带后缀；`实际板数` 是**文本**；
  `预计板数`/`ISA`/`派送计划` 在 3.1 是**公式**（只读，通过链接解析）。
- lark-cli 两个坑：payload 文件必须相对路径；`--filter-json` 用数组式条件。
- 首批生产写入：BEAU6279991 的 5 条按路线汇总记录（后来沉淀为 📦 库存导入）。
- 旧项目（预报同步 `sync.js`/`local_db`）先归档于 `archive/`，**2026-10-02 LTS
  清理时移出工作树**（仍在 git 历史：`956a756`）。

## 2026-07-24 · 写权限调研与 5.6 上传原型

- 在 `3.1 测试表 tblmAEVldrBdd460` 做 create→读回→delete 确认 App 可写。
- 学到并固化的规则：**写不存在的选项名会自动新建选项** → 所有单选写入前必须
  命中实时选项；双向链接写一侧即可；`复制时间列` 是文本不是日期。
- 原型 `upload_56.py`（文件解析 → 直接登记 5.6）跑通了 dry-run/守卫，但它与后来的
  ①/② 形成**第三个写 5.6 的入口** → 2026-08-04 退役，2026-10-02 文件移除。

## 2026-07-29 → 07-31 · webapp 预约同步成型

- 用户现场**没有 Node**，所以 webapp 选择**纯标准库 Python**，零依赖——这是至今
  的硬约束（只有删除监听器例外，单独隔离）。
- 建 dev 副本表（3.1/5.6/5.2 副本），`LARK_ENV=dev`；**dev 永不写共享生产 5.x**。
- "执行按钮有时卡住" → 根因是 10–90 秒的飞书调用链跑在请求里、重复提交无声排队、
  套接字超时未包装。解法：后台 job + 轮询进度 + 单飞提交 + 刷新重连 + 30s 超时重试。
- Feishu `client_token` 必须是 UUID v4 **且永不重复**（重放缓存比记录活得久）。

## 2026-08-04 → 08-05 · 规则定稿（用户逐条指定）

- **每张表一个写入者**：用户看到 ② 对已有预约显示"新建行程"很困惑，且要求零重叠
  → ① 只建 5.6；② 只更新 3.1/建 5.x/改**已关联**的 5.6；上传页只解析不写。
- **复制时间列存储格式 = `MM/DD/YYYY HH:MM`**（用户指定；早期按 2025 年样本行
  写成年在前被指出有误，已修复 3 条）。所有比较走 `norm_time()`，新旧格式兼容。
- **计划不一致 = 最新提交优先**（newest-wins）：同 ISA 新时间→改时间；新 ISA 已存在
  →改挂；全新 ISA→原地改写。
- **拆柜**（同柜号+路线多行）：先按箱数、再按**实际板数**（用户明确不用预计板数）
  区分；分不开就拦截列出候选。
- **目的地校验改为实时读取 5.6 选项**（用户加 XCAB 被 config 枚举拦住 → 结论：
  选项类在飞书改，结构类改代码）。
- ① 新建预约独立成页；实测搜索索引对新记录延迟约 5–7 秒 → 进程内 recent-creates
  缓存兜底去重。
- 首次生产运行 ZCSU9034790B 三路线全部核实无误。

## 2026-09-03 · 🗑️ 删除追踪

- **问题**：3.1 记录丢失，Base 自动化无法以删除为触发；飞书自带历史在多表高频
  操作下只能看约 30 分钟且 diff 加载不出；角色权限没有"删除"粒度。
- 设计了四层（历史记录 / 事件监听 / 快照比对 / 高级权限），用户基于上述现实
  **选择事件监听 L1**：`drive.file.bitable_record_changed_v1` 的 `record_deleted`
  自带 `before_value`（被删内容）、操作人、时间。
- 现场发现：租户在**国际版 Lark**——REST 两个域都通，但 ws 长连接必须用
  `open.larksuite.com`；`lark-cli event consume` 不封装该事件，故用 `lark-oapi` SDK。
- 用户逐条收敛：**只记录新增+删除，不记录编辑**（编辑是体积洪峰）；日志 >5 GB 警告
  但绝不自动删；需要**本地条件删除**（免搜索勾选）；表格以 **柜号/AWB 替代 record_id**。
- 操作人/表名解析：open_id 在飞书界面不可见且按 App 隔离 → 用各表 创建人/修改人
  自动采集（`identity_harvest.py`）；手工别名表曾存在一天，用户要求**移除以保持
  通道干净**。表名改为从 Base 实时表清单解析。
- 两个 Task Scheduler 服务（webapp + 监听器）接管常驻运行。

## 2. 写入 API（已学习，官方文档）

**建单条**：`POST /open-apis/bitable/v1/apps/:app_token/tables/:table_id/records`
**批量建**：`POST …/records/batch_create` — 单次 ≤ **1000 条**，限速 **50 次/秒**，
支持 `client_token`（UUID v4）**幂等**，重试不会重复建。

字段写入格式（按类型）：

| 类型 | 写入格式 | 备注 |
|---|---|---|
| Text | 字符串 | |
| Number | 数字 | |
| **SingleSelect** | 选项名字符串 | ⚠️ **写一个不存在的选项名会自动新建选项** |
| MultiSelect | 字符串数组 | 同上风险 |
| **DateTime** | **Unix 毫秒**（int，如 1674206443000）| 绝对时刻，时区只影响显示 |
| Checkbox | 布尔 | |
| SingleLink / **DuplexLink** | **record_id 字符串数组** `["recXXX"]` | 写一侧会自动同步另一侧 |
| Attachment | `[{"file_token": "..."}]` | 需先上传素材拿 token |
| User | `[{"id": "..."}]` | |

单表上限 2 万条；同步表不可写。

## 3. 数据模型约束（决定"上传"到底怎么写）

> [!warning] 3.1 里的 ISA / 预约时间 / 派送计划 都是**公式字段（只读）**
> 不能把计划里的预约号/时间直接写进 3.1。它们是通过**链接**从 5.6 / 5.x 解析出来的。

各表可写字段实况（`webapp/lark_client.py` field_meta 读取）：

- **3.1 库存总表**（155 字段，52 可写）：可写 `柜号/AWB`(Text)、`目的地路线`(Select)、`仓库供应商`(Select)、`实际板数`(Text)、`箱数/重量/体积`(Number)、`5.2~5.5`(DuplexLink→计划表)…；**只读**：`ISA`、`预约时间`、`派送计划`、`预计板数`、`出库时间`、`库存自动编号`…（全是公式）。
- **5.6 预约表**（16 字段，11 可写）：可写 `ISA`(**Number**)、`目的地`(Select)、`预约账号`(Select)、`复制时间列`(**Text**)、`5.1~5.5 出库计划`(DuplexLink)；只读：`预约时间`(公式，源自 `复制时间列`)、`已预约标识`…
- **5.2 BESTAR-CAL**（等 5.x 计划表）：可写 `库存信息-卡尔加里`(DuplexLink→3.1)、`预约信息`(DuplexLink→5.6)、`预约账号`(Select)、`出库时间`(DateTime)…；只读：`ISA`、`出库板数`(Lookup)、`预约时间`(公式)。

**含义**：预约号+时间存在 **5.6**（时间是 `复制时间列` **文本**，非 DateTime）。3.1 与预约的关联，是靠 3.1↔5.x↔5.6 的**双向链接**串起来的（正是 [[Appointment Sync Runbook]] 那套）。

- 5.6 `目的地` 选项（23）：YYZ*/YOO1/YHM1/YXU1/YGK1/YOW*/YVR*/YYC*/YEG1/YEG2/XYY*/XCAB —— 计划里的 YYC4/YEG1/YEG2/YVR4/YVR2 **都是合法选项**；但 UPS/PUROLATOR/AST/私人地址 **不是**。
- 5.6 `预约账号` 选项（21）：S3/S7/SS/…/BESTAR/WBLL/GFL/DINO/元浩… 
  → **`预约账号` = 页面上所选的「仓库供应商」**（用户 2026-07-24 确认）。上传时取 `仓库供应商` 下拉值。
  > [!warning] 真实写 5.6 时的映射坑（沙盒文本无所谓）
  > 5.6 `预约账号` 是**单选**。`BESTAR/WBLL/GFL/DINO` 在选项里可直接用；但 **`VAST` 要映射成 `元浩`**（见 config `accountAlias`），`CAL-5505`/`TOR-1140` **不是**合法 `预约账号` 选项 → 写前必须校验/映射，否则会新建垃圾选项。
- `复制时间列` 现存格式：**`2025/03/18 20:00`**（`YYYY/MM/DD HH:MM`，无秒无时区）。写入要对齐这个格式；计划里的 `07/24/2026 09:00 MDT` 要转成 `2026/07/24 09:00`（丢时区，与现存一致）。

## 5. "上传"可能的三种落点（待用户确认意图）

| 方案 | 做什么 | 写入面 | 风险/复杂度 |
|---|---|---|---|
| **A. 只建/补预约（5.6）** | 计划里缺失的预约号在 5.6 建记录（ISA/目的地/复制时间列[/预约账号]）| 仅 5.6 | 中：需 `预约账号`（计划缺）；需按 ISA 去重（10/12 已存在）|
| **B. 全量关联（推荐对齐 runbook）** | 每个 柜号×路线：定位 3.1 行 → 建/找 5.x 车次 → 关联 5.6 预约 ↔ 3.1 行；板数写 3.1 `实际板数` | 3.1 + 5.x + 5.6（含双向链接）| 高：多表 + 链接，最贴近现有工作流 |
| **C. 落到暂存/测试表** | 把解析出的计划原样写进一张测试/新表，供人工核对再决定 | 仅测试表 | 低：不动真实工作流，最安全的第一步 |

## 6. 安全上传流程（提议）

1. **确认写权限**：在 `3.1 测试表` 建 1 条测试记录 → 读回 → 删除。（需人工点头）
2. **校验守卫**：写任何 SingleSelect 前，值必须命中现存选项（`目的地`/`预约账号`/`目的地路线`），否则**停下问人**（避免自动新建垃圾选项）。UPS/PUROLATOR/AST/私人地址 等非标准路线**不进预约/路线选择字段**。
3. **按 ISA 去重**：先查 5.6，存在则不新建。
4. **幂等**：批量写用 `client_token`（UUID v4），重试不重复。
5. **Dry-run**：先在测试表/安全模式下产出"将要写什么"，给操作员看，签字后再对生产表跑。
6. **一次一票**的纪律仍在（[[Production Guardrails]]），批量时逐条可回溯、可记录。
